# Phase 3 delivery plan: optional accounts and two-device sync

Prepared: 9 October 2026, Pacific/Auckland.
Status: proposed delivery sequence under the accepted architecture; planning only.

Visual reference: [Phase 3 architecture diagrams](../architecture/phase-3-sync.md)
show the component boundaries and the path of an edit between devices.

## Outcome and boundaries

A user can optionally sign in with GitHub on Android and Windows, explicitly
copy guest tasks into an account, and see changes arrive automatically on the
other foreground device. Offline edits remain durable. Concurrent edits either
merge safely or remain available for explicit recovery. Signing out, switching
accounts, expired credentials and backend outages preserve local work.

SQLite remains the only UI read/write path. Supabase Auth/PostgreSQL sits behind
domain ports. The [accepted architecture](2026-10-03-offline-first-architecture.md),
especially sections 5, 8 and 9, remains normative. This plan sequences that work;
it does not authorize implementation, production deployment or publication.

Recurrence, calendar, reminders and snooze remain Phase 4. Full portable
import/export UX and signed release distribution remain Phase 5. Phase 3 does
need a usable recovery export before offering account deletion or removal of
unsynced local data; it cannot rely on a future feature to prevent data loss.

  Android fresh-install/offline/process-restart acceptance remains open.

  using the checklist in [Phase 2 verification](../verification/phase-2.md).

  implementation starts. Planning can proceed now. Retain separate Windows

- Schema v1 reserves sync tables, but has no implemented upgrade path.

  not establish whether it is installed elsewhere. Backend/account configuration

## Decisions to resolve in 3.0

The accepted product choices remain Flutter/Drift, optional Supabase, GitHub
OAuth/PKCE, separate profile files and per-field concurrency. No new provider
decision is needed for this plan. Resolve these implementation details in a
protocol contract with executable fixtures before enabling account writes:

1. Define typed versioned requests/results for apply, pull, snapshot, conflict
   resolution and device registration. Include original base values, field
   groups, predecessor references, payload identity, size limits and explicit
   rejection/recovery results. Version changes must update golden fixtures;
   a local schema version and a wire protocol version are separate decisions.
2. Specify how a successor binds to its predecessor's accepted field revision
   without changing any payload that may already have been sent. Resolve the
   interaction between held dependent edits, contiguous device sequences and
   progress for unrelated entities. A conflicted predecessor must not block
   the entire account indefinitely; do not skip assigned sequences or quietly
   rebase the original edit. Prove this with a conflict/dependent/unrelated
   three-operation fixture before choosing the queue representation.
3. Define entity-kind-qualified identities for shadows, tombstones and field
   versions, including composite task/tag memberships and preference keys.
   Specify cross-owner references and normalized tag-name collisions, plus
   safe default-view behavior when the referenced view is deleted.
4. Define restore preconditions, partial-field acceptance and resolution races.
   Keep due values, status/completion and view query specifications atomic.
   Test both server orderings of edit/delete: visibility must remain deleted
   while meaningful concurrent edits remain recoverable.
5. Plan the minimal SQLite upgrade for staging, original bases, pending states,
   conflict metadata and adoption manifests. Expect v2 if structural changes
   are needed; retain v1 snapshots and generated fixtures. Never repurpose a
   reserved table without documenting its durable semantics.

## Implementation responsibilities

- `lib/domain`: typed protocol values, command policies and provider-free ports.
- `lib/data/local`: migrations, accepted shadow, visible pending projection,
  atomic local/remote apply, durable checkpoints and adoption destination writes.
- New application orchestration: one worker per profile, lifecycle triggers,
  profile generations, retries and explicit recovery states.
- Provider/platform adapters: Supabase transport/auth and native secure storage
  and redirect registration. Do not let UI widgets call provider tables directly.
- `lib/app`: account entry, adoption preview, progress/status, conflict review,
  reauthentication, sign-out/switch and deletion flows using local state.
- New `supabase/`: config, migrations, SQL/integration tests and narrowly scoped
  server deletion support. Privileged credentials remain server-side.

Local commands must continue committing entity/history/outbox/dirty changes in
one transaction. Remote page application and cursor advancement are atomic;
downloads update accepted state then replay pending work with original bases.
Network requests and OS actions stay outside local transactions.

## Required recovery and security behavior

The server account-row lock covers revision allocation, entity changes,
conflicts, receipts and logs through commit. Pull pages never split a revision.
Permanent validation rejection consumes its sequence with a recoverable result;
network/auth failure consumes nothing. Duplicate accepted operations cannot
reapply, even after detailed receipts expire.

Keep the accepted retention policy: change logs/receipts 180 days, deleted
content 30 days, resolved conflicts 90 days, unresolved conflicts until explicit
resolution, and minimal deletion identities/device watermarks until account
deletion. Snapshot tokens expire after 24 hours. Exercise retention with test
clocks/fixtures, including stale updates, expired receipts and server-epoch
changes. Do not prune pending work to make sync appear successful.

Snapshots stage durably and install atomically after validation. Token expiry
restarts staging only; existing local work survives. Guest adoption uses a
resumable manifest and stable account-scoped lineage mappings, including repeat
adoption on another device. Cross-file operations are not one transaction.
The account's existing entities/tombstones take precedence over collisions;
copy or restore requires an explicit choice.

Sign-out retains pending work by default and removes active credentials. An
expired session in an already-open account still permits offline editing;
reopening an explicitly signed-out profile requires that account's authentication.
Every async response is scoped to profile plus generation. Account deletion
requires recent authentication, explicit confirmation, a working export option,
immediate access denial and resumable cleanup. Old devices cannot recreate the
deleted account. Offline copies remain on their devices until removed.

## Verification and completion

Use the [two-device runbook](../runbooks/two-device-testing.md), with synthetic
accounts X/Y and a real development backend. Phase 4 recurrence/notification
steps in that runbook remain deferred. Required Phase 3 evidence includes:

- Every existing task/tag/membership/milestone/order/view/default command,
  with equivalent-value acceptance, independent merges and conflicting groups.
- Duplicated/dropped responses, late server commits, process termination,
  interrupted pull/snapshot, expired auth/cursor, backend outage/read-only mode,
  both reconnect orders and concurrent conflict resolutions.
- Anonymous/cross-owner reads and writes through raw REST and RPC, including
  logs, snapshots, conflicts, adoption mappings and deletion endpoints.
- Android and Windows native OAuth/secure-storage behavior, profile isolation,
  adoption retry, local editing during download and pending-safe account exit.
- At least 100 alternating foreground changes with realtime enabled and another
  100 with realtime disabled. Use a common monotonic harness or calibrated
  clocks; measure local commit to second-device display, with no manual refresh.
  Target p95 <=5 seconds normally and <=35 seconds with polling fallback under
  healthy backend/RTT <=150 ms conditions. Include a 10,000-task fixture to test
  the accepted scale; the current whole-workspace query projection is a risk to
  measure, not a reason to promise untested performance.

Run relevant SQLite/domain/widget/server tests for each change, then the repo
quality suite and available Android/Windows builds. Apply the migration skill
for generated schema/helper commands and retained-data upgrades. Pin exact CLI
commands after checking the installed version's help; do not record planned
commands as executed results. A native build or mock transport test cannot close
the installed two-device gate.

Prepare least-privilege backend CI without production secrets, using Actions
pinned to commit SHAs. Prepare a protected manual deployment job only after
empty-database/upgrade/RLS tests and backup/restore rehearsals exist. Server
restore must change epoch and preserve client recovery paths. Production apply,
push/publication and store distribution are outside this planning request.

Update README, backlog, setup/backend/cost/recovery runbooks and
[Phase 3 verification](../verification/phase-3.md) as evidence arrives. Phase 3
is complete only when the real integration, native identity and two-device
gates pass. Phase 4 waits for that result.

## External prerequisites and provider checks

Implementation needs a working local container runtime and pinned Supabase CLI,
a GitHub OAuth application configured with exact redirects, a development
backend reachable from both devices, and Android/Windows test access. A phone
cannot use the PC's localhost. Keep development network exposure restricted;
do not put provider secrets in chat, application config or source control.
Missing configuration should leave only the dependent tests open.

Official sources reviewed for this plan on 9 October 2026:

- The [local development workflow](https://supabase.com/docs/guides/local-development/cli-workflows)
  uses the CLI and a Docker-compatible runtime. Validate actual host readiness
  during 3.0; planning did not start containers or install tooling.
- The [Flutter client maintainer documentation](https://github.com/supabase/supabase-flutter/blob/main/packages/supabase_flutter/README.md)
  describes native deep links and custom persistence. Its default uses shared
  preferences for sessions and PKCE verifiers. Explicit secure persistence and
  account isolation are therefore implementation requirements; package support
  alone is not native acceptance evidence. Recheck the exact pinned release.
- [Pricing](https://supabase.com/pricing) and
  [project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)
  retain the Free-plan availability/backup limitations relevant to this design.
  Keep local operation independent of cloud availability, avoid artificial
  keepalives, and recheck numerical quotas before provisioning.
